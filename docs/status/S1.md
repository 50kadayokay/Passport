## a08: unpublished releases leave Mine IQ (decided 2026-11-01)

The decision: "When a release is unpublished, remove its full text and facts
from active Mine IQ retrieval. Preserve historical audit records, but do not
present unpublished material as current public information."

**No migration and nothing deleted.** Retrieval filters at read time; updates,
release_revisions, activity_log and facts rows are untouched.

- **The rule** (`src/lib/mineiqActive.js`, shared by server and portal):
  - A release is active only if its **passport** publication is `published`.
    `unpublish_publication` flips the publication, not `updates.status`, which
    is why `mineiq_search` alone still matched taken-down releases.
  - A fact is active only if its own publication is `published` (an inner
    join). If the publication is deleted, `facts.publication_id` is set to null,
    so those facts drop out too.
- **Server** (`api/_mineiqSearch.js`):
  - After `mineiq_search`, two reads run with the caller's JWT for just the
    returned ids, then `keepActive()` filters the results. That read can only
    narrow what came back, never add to it.
  - The search asks for `limit*2` (max 50), so dropped rows don't shorten the
    answer.
  - If the liveness reads fail, all releases and facts are withheld,
    documents are kept, and the result is marked `degraded`.
  - The legacy scan (RPC missing) reads `publications(destination_id,status)`
    and applies the same rule.
- **Portal** (`src/lib/mineiq.js`):
  - Fact count, facts by category and the fact list count live facts only.
  - The overview's "published releases" and "recently learned" exclude
    taken-down releases (demo fixtures, which have no publications, keep
    their status).
  - `factCountForPublication` still counts all of that release's facts, for
    the take-down notice.
- **Copy:**
  - The take-down confirmation now says: "MineIQ stops using this release and the N facts it learned
    from it in answers and drafts. They are kept as a record, and come back if
    you publish again."
  - The taken-down view and the library notice match. Checked
    in the /portaldemo browser.
- **Republish** restores everything: the rows never went anywhere.
- **Revised** releases: the release row is synced on every saved correction,
  and the listener supersedes facts a correction changed. Only the current
  body and the current facts come back.

**Known limit (no migration):** if a taken-down release's fact had
superseded an older fact from a still-live release, the older fact stays
hidden by `mineiq_search`'s `superseded_by is null`. The older release's own
text is still retrieved. Fixing that properly means changing `mineiq_search` in
0080 (revive a fact whose superseder is retired). That's optional and isn't done here.

## Capture-on-apply for the production runner (S4's audit: drifted functions)

The 2026-11-01 read-only audit found production's `publish_publication`, `claim_deliveries` (0071), `company_go_live` (0072) and `accept_company_invitation` (0076) differ from the repo, so the repo rollbacks would restore repo text. The runner now captures production's own text first. Built, offline only, never run against production.

- `scripts/_function-capture.mjs` (new): `functionTargets(sql)` pins every function a file creates, replaces, alters, drops or grants/revokes on, including DO-block grants on literally named signatures. It fails CLOSED on unqualified or quoted names, OUT/INOUT/VARIADIC/%TYPE, procedures, DROP … CASCADE, ON ALL FUNCTIONS, and DO blocks that create functions or grant on unnamed ones. Every pending file parses; 0071: 4, 0072: 7, 0076: 11.
- Apply order: marker → **capture** (READ ONLY transaction: `pg_get_functiondef`, owner, ACL, overloads; an unknown argument type refuses) → capture file written or nothing runs → pre-snapshot → begin → captured functions re-read and must be unchanged → the file → commit.
- The file goes to `supabase/audit/results/apply-capture-<file>-<timestamp>.sql`. The CLI checks that path is gitignored before reading the DSN. The file is mode 600 and never overwritten. It holds the bodies verbatim (create or replace), then a revoke of all current grants, then the captured grants, then a verify block (md5, ACL and owner must match, or it raises). It is one transaction. Functions new in the file are listed, not dropped: the repo rollback removes them. Its sha256 and path are logged as `status: "captured"`.
- Secret-like strings in bodies (JWT, Stripe/Supabase/provider keys, DSNs with passwords, private keys, assigned secrets) are reported by kind and count only. Bodies never reach stdout.
- The plan prints a `capture:` line per step: N functions with their names, `none`, or `AMBIGUOUS` (which checkRequest refuses before the DSN is read).
- Tests: `scripts/apply-capture-test.mjs` 62/0, run under the no-network preload and added to `check:s1-prod-runner` (with the runner's 114/0). Mutation-checked: removing the in-transaction recheck fails 2 tests.

## No-transaction path for 0065c / 0073a (no more "by hand" steps)

- `scripts/_concurrent-indexes.mjs` (new). `parseConcurrentFile` accepts only these, and refuses the whole file on anything else (mixed statements, BEGIN, ordinary CREATE INDEX, REINDEX, CASCADE, multi-index DROP, unnamed or quoted index, unqualified table, a name used twice, no index statement):
  - `CREATE [UNIQUE] INDEX CONCURRENTLY [IF NOT EXISTS] <name> ON [ONLY] schema.table`
  - `DROP INDEX CONCURRENTLY [IF EXISTS] schema.name`
  - `ANALYZE`
  - comments
- `applyConcurrent` (in `_production-migrations.mjs`) uses the same flags, exact ref, typed confirmation, one file, `--approved-by`, DSN checks and log as `--apply`. The order is: role check → marker false → pre-snapshot → statements → marker → post-snapshot and diff.
  - It never sends BEGIN. Each statement gets `SET statement_timeout` (create 20min, drop 2min, analyze 5min) and `lock_timeout = '3s'`; both are reset after.
  - After each CREATE, `pg_index` must read valid and ready. An INVALID index stops the run and prints `RECOVER: DROP INDEX CONCURRENTLY IF EXISTS <name>;` then retry. That covers a build that ends invalid and a lock timeout that leaves a half-built index.
  - An INVALID index left by an earlier run refuses before anything runs, because IF NOT EXISTS would skip it.
- The checkpoint is now the audit marker AND every index present, valid and ready. The plan refuses unless the rollback is DROP INDEX CONCURRENTLY of every index built. The plan shows both files as `[CONCURRENTLY: runner, no transaction]` and says how the rollback runs.
- `--record-manual` is kept as a fallback for one run by hand anyway.

## Rollback mode for the production runner (S2's gap: the log said "applied" after a rollback)

- `--rollback --only <file> --ref=… --approved-by=… [--accept-data-loss="<decision>"]` uses the same flags, exact ref, typed confirmation and DSN checks as an apply. Logic is in `scripts/_production-rollback.mjs` (new).
- It refuses, before the DSN is read:
  - 0000, 0059 and 0067 (NEVER_ROLL_BACK)
  - a file this runner did not apply (per its log)
  - anything but the most recently applied file (strict reverse order)
  - 0071 while 0088 is applied (ROLLBACK_BLOCKED_WHILE, mirroring the SQL guard)
  - a file another applied file still needs (manifest PREREQUISITES, and 0058 while 0077 is applied)
  - a lossy rollback without `--accept-data-loss` (≥8 characters, logged). Lossy means the rollback's own top-level statements drop tables or columns, delete, truncate, or drop with CASCADE, or the rollout table says "lossy". Function bodies and GRANT TRUNCATE do not count. 0071, 0074 and 0076 are flagged because their SQL drops columns or tables; that fails closed.
  - a capture file the log names that is gone, changed (sha256) or does not parse
- Transaction files: marker must read applied → pre-snapshot → ONE transaction (committed rollback, then that apply's capture file) → marker must read NOT applied → commit → post-snapshot and diff. CONCURRENTLY files run their DROP INDEX CONCURRENTLY one at a time with no transaction.
- Log: `rollback-started` / `rolled_back` / `rollback-failed`. A started or failed rollback blocks everything until `--reviewed`. `rolled_back` takes the file off the stack and the plan offers it again. An audit that says "applied" for a file the runner has rolled back refuses planning until the audit is re-run.
- The plan prints a ROLLBACK section: next, then the rest newest first, with LOSSY marks, the 0071/0088 rule, and the never list.
- The runbook in `docs/PRODUCTION-ROLLOUT-PLAN.md` ("Rolling back a migration") now uses `--rollback`. The "mark it by hand" step is gone; psql is kept only for when the runner cannot connect. check:s2-rollout-plan 19/0.
- Tests: `scripts/apply-rollback-test.mjs` 53/0 (no-network preload, in `check:s1-prod-runner`). Mutation-checked: removing the order, blocked-while, lossy, capture or post-marker checks each fails tests. npm test exits 0.
